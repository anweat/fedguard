## 0. 结论先行

整体框架（挂载点 × 权限 × 参照 × 行为确认）是对的，可以开工。开工前必须处理下面四个问题，前两个会直接卡住 P0 或让实验结论失效：

| # | 问题 | 性质 | 影响 |
|---|---|---|---|
| ① | FedLLM-Attack 固定的 `transformers==4.31.0` **无法加载 Qwen2.5（需 ≥4.37）和 Llama-3.1（需 ≥4.43）**；Flower 1.40 要求 **Python ≥3.11** | 环境阻断 | 确认单第 7 节选的模型在实验平台上跑不起来 |
| ② | 方向 A 的"效果层"特征如果直接用上传的 BᵢAᵢ，比较的是**累计效果**，不是**本轮增量**。几轮之后全局部分占主导，客户端之间的余弦会趋近 1，区分度消失 | 算法正确性 | Q1 的对比实验可能得出错误的负结论 |
| ③ | 默认配置是 10 个客户端每轮抽 3 个（`sample_clients=3`），其中 3 个恶意。约 **18% 的轮次恶意方占多数**，而且 3 个点上算中位数/MAD 没有统计意义 | 威胁模型假设 | "同轮横向"参照在默认配置下基本不可用 |
| ④ | 威胁轴缺少**自报元数据攻击**、**自适应攻击者**、**先潜伏后攻击**三类，都是评审一定会问、而且会直接击穿当前设计的攻击 | 覆盖缺口 | 详见第 1 节 |

另外有一个命名问题：确认单里"系统轴 S1–S6"和"威胁场景 S0–S5"都用了字母 S，P2"跑 S0"、P3"跑 S1"会产生歧义。**建议把威胁场景改名为 C0–C5**（C = case），下文统一用 C。

## 1. 威胁面复查

### 1.1 必须补进矩阵的威胁

| 缺口 | 为什么必须补 | 建议 |
|---|---|---|
| **自报元数据攻击** | FedAvg 按客户端**自报**的样本数加权。在 FedLLM-Attack 模拟中 `sample_num_list` 取的是真实数据集长度，所以看不到这个问题；到了 Flower，它来自客户端写的 `num-examples`。恶意方虚报 100 倍样本数就能让自己的更新主导全局，而且更新本身完全"正常"。伪造 loss、伪造检测摘要也属于这一类 | T2 攻击对象增加"元数据/自报值"。H4 增加一个很便宜的插件：样本数截断或等权、自报 loss 与更新大小做一致性校验。**P0 就应该实现，模拟适配器也要改成读"自报值"而不是真实长度** |
| **自适应攻击者**（知道防御） | 之前文档里的 S4（写法归一化）只覆盖了"针对因子层检测"的情况。知道方向 A 的攻击者会直接在效果空间约束更新：把 ‖ΔW‖ 限制在良性范围内、让方向贴近良性均值（constrain-and-scale、带范数约束的 PGD 这类思路）。如果只报告对非自适应攻击的效果，论文站不住 | 增加 T7"攻击者知识"：不知道防御 / 知道算法 / 知道算法和阈值。每个主力检测器至少配一个自适应对手；统计层被绕过时，由行为层（H6）兜底，这正好体现多视角的价值 |
| **先潜伏后攻击** | 可信度累积（CUSUM/EMA）天然有利于"先正常参与、攒够可信度再攻击"的对手。如果高可信度能降低检测强度或抬高权重，攻击反而更容易 | T4 增加"潜伏后攻击"。设计上约定：**可信度只影响处置力度，不跳过检测**；单客户端的聚合权重设上限 |
| **良性微调本身导致安全退化** | 已有研究（Qi 等，ICLR 2024）表明，用完全良性的数据微调对齐模型也会降低拒答率。所以在 C0 下，每个簇的安全指标也会下降。如果阈值取"相对基座模型"，簇级行为验证会把良性簇误判为投毒 | C0 必须记录**安全指标随轮次的良性漂移曲线**；行为验证的参照改成"同轮其他簇 / 同轮良性漂移"，不能用基座模型 |
| **抽样下诚实多数不成立** | 见结论 ③。横向参照、Krum、中位数都依赖诚实多数 | S1 抽样与 T5 规模要做交互实验；判定引擎**按本轮参与人数自动降级**（例如少于 5 人时关闭横向 z 分数，只用历史和可信参照） |
| **攻击检测系统本身** | ① 生产环境没有干净的 C0，如果阈值用在线数据估计，攻击从第 1 轮开始就会**污染基线**；② 探针集固定且被攻击者知道时，攻击者可以只在探针覆盖不到的话题上破坏安全；③ 客户端上传 NaN/Inf、形状错误或超大张量，可能让服务器上的统计量甚至进程崩溃 | ① 见 3.2 节"校准"；② 探针从大池子中每轮随机抽取，对客户端保密；③ 核心库第一层就做输入校验（形状、dtype、有限值、范数上限），并禁止用 pickle/`torch.load` 读取任何客户端来源的数据，统一使用 safetensors/numpy |

### 1.2 明确声明为本期不做（写进盲区表）

| 威胁 | 理由 |
|---|---|
| 隐私攻击（梯度反演、成员推断） | 不属于投毒。但**记录层保存逐客户端 LoRA 会扩大隐私泄露面**，产品侧需要写明保留策略和访问控制 |
| Sybil（一方伪造多个身份） | 跨机构场景有准入审核，默认假设身份可信；"多个协同"已覆盖其效果 |
| 搭便车（直接回传全局参数或噪声） | 影响公平，不是投毒；不过它会出现在特征分布里，C0 可以顺便标注 |
| 异构 LoRA（各客户端的秩或目标模块不同） | 本期假设同构；输入校验拒绝不一致的形状 |
| SecAgg 与逐客户端检测共存 | 需要带范数证明的安全聚合这类方案，超出本期范围；v1 产品明确为"检测模式"和"SecAgg 模式"二选一 |
| 未知触发器后门的完备检测 | 探针无法枚举未知触发器，只能标注为盲区 |

## 2. 防御面复查

### 2.1 方向 A 的增量定义（必须在 P1 之前定下来）

上传的是 LoRA 当前值，不是变化量。本轮真正的功能变化是

```text
ΔWᵢ⁽ᵗ⁾ = s · (Bᵢ Aᵢ − B_g A_g) = s · [Bᵢ, −B_g] · [Aᵢ ; A_g]      （s = alpha / r）
```

它的秩不超过 **2r**，所以原来的 r×r 技巧可以原样用在 2r×2r 上，范数、内积和谱都仍然精确，不需要展开大矩阵。需要注意的几点：

- **不要用 (Bᵢ−B_g)(Aᵢ−A_g)**：它漏掉了一阶项 ΔB·A_g + B_g·ΔA，而这恰恰是更新的主体。
- **累计效果 BᵢAᵢ 仍然有用**：κ（写法冗余度）是在累计因子上定义的，保留为一个特征。
- **"全局方向"要用真实的全局变化**：FedAvg 之后的全局效果是 (ΣwB)(ΣwA)，不等于 Σw·BA。
- **前几轮不稳定**：LoRA 的 B 初始化为 0，第 1 轮的 A 基本是随机初始化。前 k 轮不参与阈值校准（k 由 C0 实测确定）。
- **学习率随轮次衰减**：FedLLM-Attack 使用按轮次的余弦学习率，更新的大小会系统性地变小。**所有与大小有关的特征都要按轮次归一化**（除以同轮中位数或当前学习率），否则第 90 轮会用第 10 轮的阈值。
- **批量计算**：把本轮所有客户端的 U=[Bᵢ,−B_g] 拼成 d×(2r·n) 的矩阵，一次 GEMM 算出 Gram 矩阵，不要逐对循环。

### 2.2 挂载点与处置的补充

| 补充 | 说明 |
|---|---|
| **H0 准入 / 承诺** | L1（承诺 + 抽查）要求客户端在**训练前**提交数据集的 Merkle 根，现有的 H1–H8 里没有这个位置。同时 H0 也是身份与可信等级登记的地方。P0 只需要在接口里预留，不实现 |
| **D7 处置增加"复核 / 恢复"** | 良性机构被误判后要有恢复路径：可信度随时间恢复、人工复核、申诉。否则跨机构场景没人愿意用 |
| **D7 处置增加"要求抽查"** | 可疑时要求客户端升级到 L1，与可信等级设计闭环 |
| **可信参照的前提** | "服务器用可信数据训练参照更新"需要服务器有数据和 GPU。它是 O2 + 可信数据，不是免费的，产品配置里要写成可选能力 |

### 2.3 修订后的覆盖表

| 场景 | 主观察点 | 兜底 | 盲区 |
|---|---|---|---|
| C0 无攻击 | 全部（测误报与良性漂移） | — | — |
| C1 恶意客户端数据投毒 | H4 效果特征、H6 行为 | H8、回滚 | 统计贴近良性且探针覆盖不到的行为 |
| C1′ 自报元数据攻击 | H4 一致性校验、H5 权重上限 | — | 小幅虚报 |
| C2 诚实客户端被分散污染 | H1、H2（客户端） | H6 | 服务器侧基本看不到 |
| C3 更新层扰动 | H4、H5 | H6 | — |
| C4 自适应攻击者 | H6 行为 | 多视角融合 | 同时绕过统计层和探针的攻击 |
| C4′ 潜伏后攻击 | H4 历史突变 | 可信度只影响处置不跳过检测 | 潜伏期内无法发现（本来就无害） |
| C5 服务器不可信 | H7 | 多客户端交叉验证 | 本期只预留接口 |
| 任意场景 + SecAgg | H1–H3、H7 | — | 服务器侧全部失效 |

## 3. 实际部署：性能与可用性

### 3.1 性能估算（按模型结构计算，待 P1 实测）

以 Qwen2.5-7B 为例：28 层，hidden 3584；由于 GQA，**v_proj 的输出维度只有 512**，所以之前按 4096×4096 估的数字偏大。

| 项 | 估算 | 结论 |
|---|---|---|
| 每客户端每轮 LoRA 大小（r=32，q+v） | 约 1010 万参数 ≈ 20 MB（bf16）/ 40 MB（fp32，8-bit 基座下 LoRA 通常是 fp32） | 10 客户端 × 100 轮 ≈ 20–40 GB/次实验。之前估的 33.5 GB 量级正确 |
| 效果层特征（2r=64，10 客户端，56 个模块） | 批量 Gram 约 0.2 TFLOP；GPU 上可以忽略，CPU 上几秒 | 不是瓶颈；客户端数到 100 时要改成分块计算 |
| H6 前向代理指标（拒答方向投影、有害提示上的拒答 logprob、良性提示上的 KL） | 200 条提示 × 约 128 token ≈ 0.4 PFLOP，A100 上每个候选约 1–3 秒 | **可以每轮做**，每轮只评 簇数 个候选 |
| H6 生成式评测 + judge | 200 条 × 256 token，HF generate 下每个候选需要数分钟，还要常驻一个 judge 模型 | **只在升级到等级 3 或每 N 轮做一次** |
| 一轮本地训练（10 步 × batch 16 × 512 token，7B 8-bit） | 每客户端约数十秒，每轮 3 个客户端约 2–3 分钟 | 检测预算定为**每轮时间的 10–20%**，P1 实测后固定 |

**由此得到的设计决定**：检测分为三档，逐档升级。统计特征每轮都算；前向代理指标每轮对每个簇算；生成式评测只在疑似时触发。这就是"轻量级"定位的工程含义，也要写进论文的开销表。

### 3.2 可用性问题

| 问题 | 设计决定 |
|---|---|
| **环境**：两套依赖、Python 3.9/3.10/3.11 并存 | 核心库要求 Python ≥3.10、只依赖 torch 和 numpy，并在 torch 2.0 和 2.10 下都跑一遍测试。**P0 先做一次尝试**：让 FedLLM-Attack 直接运行在 FlowerTune 的依赖（Python 3.11、transformers 4.53、trl 0.8.1、peft 0.6.2）上。trl 从 0.7.2 升到 0.8.1 改动不大，如果能跑通，就只需要维护**一套环境**。跑不通时，再单独把 FedLLM-Attack 升级到 transformers ≥4.43 |
| **生产环境没有干净的 C0 做校准** | 提供"校准模式"：前若干轮只标记不处置，基线用服务器的可信参照更新或已知可信客户端来估计，并用鲁棒统计抵抗污染。论文中要单独报告"在线校准"和"离线 C0 校准"的差距 |
| **误报的业务代价** | 默认处置档位保守（标记/降权）；剔除和回滚需要人工确认或多视角一致；每次处置都写入可解释的证据 |
| **插件故障** | 每个插件有超时；故障时的策略可配置（默认 fail-open 并记录告警，可选 fail-closed）。插件崩溃不能中断训练 |
| **对实验的副作用** | 插件禁止使用全局 `random`、`np.random` 和 torch 的默认 RNG（FedLLM-Attack 每轮用 `random.seed(round)` 决定抽样，插件改动随机状态会让"有防御 / 无防御"两组抽到不同的客户端）。H6 在共享的 `model` 上试合并之后，必须恢复 LoRA 参数和 train/eval 模式。**P0 验收时要检查：只记录插件打开前后，训练 loss 逐位一致** |
| **服务器能力不同** | 按能力分档：无 GPU 时只跑 H4/H5；有 GPU 时加 H6。量化方式要和客户端一致（FlowerTune 默认 4-bit，FedLLM-Attack 用 8-bit） |
| **记录层安全** | 使用 safetensors、按轮次分目录、数据集与实验配置哈希一起落盘；产品侧写明保留期限和访问控制 |

## 4. 修订后的开工计划

原则不变：固定基准配置，每次只改一个维度。基准配置建议改为：**10 个客户端全员参与、1 个恶意客户端、连续攻击、Dirichlet non-IID**；抽样、多恶意和时间模式作为单维变化。

| 阶段 | 任务 | 验收标准 |
|---|---|---|
| **P0a 环境尝试** | ① `git init`，把 `external/` 设为只读依赖；② 用 uv 建 Python 3.11 环境，装 FlowerTune 的依赖，尝试运行 FedLLM-Attack 的 `main_sft.py`（Qwen2.5-0.5B，2 个客户端，2 轮，Mac 上用 CPU/MPS、不量化） | 能跑通，或者得到一份明确的"需要改哪几处"清单，再据此定一套环境还是两套 |
| **P0b 核心库** | `types`（ClientUpdate 增加 `reported` 与真实值分离、H0 预留）、插件协议与**权限强制**、输入校验、记录层（safetensors）、插件运行器（超时、故障策略、独立 RNG） | 单元测试：O2 插件拿不到数据集对象；NaN、形状错误的输入被拒绝；插件抛异常时训练继续 |
| **P0c OpenFedLLM 适配器** | 在 H3/H4/H5 接入；样本数改为读取"自报值"；"只记录"插件 | 每轮每个参与客户端的 A/B 正确落盘，只记录参与本轮的客户端；从记录重算的 FedAvg 与框架结果逐位一致；插件开关前后训练 loss 一致 |
| **P1 特征** | 因子层特征；效果层特征（**2r 增量形式**，批量 Gram）；按轮次归一化；Dirichlet 划分 | 2r×2r 算法与展开大矩阵的结果数值一致（相对误差 <1e-5）；特征随轮次的曲线；实测每轮开销 |
| **P2 良性基线** | C0：IID 与 Dirichlet，0.5B/1.5B，3 个种子；记录安全指标的良性漂移 | 每个特征有按轮次的良性分布和阈值；良性漂移曲线；确定预热轮数 k |
| **P3 检测** | C1（基准配置）+ C1′ 元数据攻击；判定引擎（分位数融合、EMA 可信度、分级处置）；H6 前向代理指标；对比 Krum/Median/FoolsGold 等 | 第一张"场景 × 防御"结果表；Q1（因子层 vs 效果层）有结论；开销表 |
| **P4 扩展** | 7B 主实验；C2（对比 ProtegoFed）；C3；**C4 自适应攻击者、C4′ 潜伏后攻击**；抽样 × 多恶意交互；FFA-LoRA 消融；在线校准 vs 离线校准 | 主结果表、消融表、盲区表 |
| **P5 产品** | Flower 适配器（GuardStrategy 包装器 + 客户端 Mod + `train()` 内钩子）；多节点演示；证据可视化 | 同一批插件在 Flower 上的判定结果与模拟一致；自报样本数攻击在真实消息链路上被拦截 |

P0a 是唯一的前置阻断项，建议最先做。它的结果决定后续要维护一套环境还是两套。

## 6. 已确认的决定（2026-09-30）

- 按第 5 节的建议执行：主模型 Qwen2.5-7B-Instruct；基准配置为全员参与、1 个恶意客户端；威胁场景改名为 C0–C5；新增三类威胁；`git init`。
- **分层原则**：框架只提供**数据接口**和**基础分析原语**，不包含具体算法。每个具体位置的检测算法写成独立的**算法模块**，由模块自己组织计算。库里内置少量默认模块，用来确认流程可用，并提供基本防护。

### 6.1 三层结构

| 层 | 内容 | 不做什么 |
|---|---|---|
| **框架层**（`core/`、`views/`、`recorder/`） | 挂载点与权限模型；按权限裁剪的数据视图；模块运行器（执行顺序、超时、故障策略、独立 RNG、模块私有状态）；输入校验；记录层 | 不计算任何检测分数 |
| **分析原语层**（`analysis/`） | 纯函数、无状态、不绑定挂载点：低秩效果运算（2r 增量、批量 Gram、谱、κ）；鲁棒统计（中位数/MAD、按轮分位数）；三种参照的通用计算；可信度累积（EMA/CUSUM）；基于距离矩阵的简单聚类 | 不做判定，不读写状态 |
| **算法模块层**（`modules/` 内置 + 各自的研究模块） | 声明 `hook` 与 `permission`，在 `run(ctx)` 中调用视图和原语，输出 `Findings`；H5 的策略模块输出 `Decision` | 不直接访问框架内部，不越权读取数据 |

模块类名用 `GuardModule`，避免和 Flower 的客户端 `Mod` 混淆。Flower 的 `Mod` 只在适配器里出现，作为把我们的模块挂到消息链路上的载体。

### 6.2 模块接口草案

```python
class GuardModule(Protocol):
    name: str
    hook: Hook              # H0 … H8
    permission: Perm        # O0 … O5，运行器据此决定 ctx 中暴露哪些视图
    def setup(self, spec: RunSpec) -> None: ...
    def run(self, ctx: HookContext) -> Findings: ...

# HookContext 提供：
#   ctx.round, ctx.participants
#   ctx.updates   -> UpdateView（O2：因子、增量的低秩表示、自报值与校验值分离）
#   ctx.history   -> HistoryView（按客户端的上次参与记录）
#   ctx.probe     -> ProbeView（O3：试合并上下文管理器，退出时自动恢复参数与模式）
#   ctx.data      -> DataView（O0，仅客户端侧挂载点）
#   ctx.upstream  -> 本轮更早挂载点的 Findings（只读）
#   ctx.state     -> 本模块的私有状态（由记录层持久化）
#   ctx.rng       -> 由 (种子, 模块名, 轮次) 派生的独立随机数发生器
# 访问未授权的视图会抛出 PermissionError。
```

### 6.3 内置默认模块

| 模块 | 挂载点 | 作用 | 用于 |
|---|---|---|---|
| `report_guard` | H4/H5 | 样本数截断或等权；自报 loss 与更新大小做一致性检查 | C1′ 的基本防护 |
| `norm_bound` | H5 | 按良性分布对效果增量的范数做裁剪 | 基本防护，对照更新层扰动 |
| `factor_stats` / `effect_stats` | H4 | 只输出因子层和效果层特征，不判定 | Q1 对比、C0 良性分布 |
| `robust_outlier` | H4 | 在指定特征上做横向或历史的鲁棒 z 分数；参与人数不足时自动降级 | 最简单的可用检测器 |
| `refusal_probe` | H6 | 前向代理指标：有害提示上的拒答 logprob、良性提示上的 KL | P3 的行为层确认 |
| `tiered_policy` | H5 | 默认处置：只标记和降权；剔除需要多视角一致 | 默认策略，保守 |

落盘由框架的记录层完成，不需要单独的模块。Krum、Median、FoolsGold 等鲁棒聚合基线直接复用 FedLLM-Attack 和 Flower 自带的实现，通过适配器配置切换，不在库里重写。
