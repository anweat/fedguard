## 1. OpenFedLLM 源码结构

核心代码约 900 行（不含评测和 1215 行的对话模板文件），结构非常扁平：

```text
OpenFedLLM/
├── main_sft.py              # 联邦 SFT 主循环（124 行）：所有流程都在这一个文件里
├── main_dpo.py              # 联邦 DPO 主循环
├── config.py                # FedArguments（联邦参数）+ ScriptArguments（训练参数）+ LoraConfig
├── federated_learning/
│   ├── fed_global.py        # get_clients_this_round()：抽样；global_aggregate()：聚合
│   ├── fed_local_sft.py     # 构造本地 Trainer（普通 / FedProx / SCAFFOLD）
│   ├── fed_local_dpo.py
│   ├── split_dataset.py     # split_dataset()：只实现了 IID；get_dataset_this_round()：每轮抽样本
│   └── fed_utils.py         # FedOpt / SCAFFOLD 的辅助状态
├── utils/
│   ├── process_dataset.py   # 各数据集转成 instruction/response 格式
│   ├── template.py          # alpaca / vicuna 模板
│   └── merge_lora.py        # 训练后把 LoRA 合并进基座
└── evaluation/              # MT-Bench、FinGPT 等评测
```

**特点**：
- **单进程模拟**：所有客户端共用一个 `model` 对象，按顺序切换 LoRA 参数来训练，没有网络通信。
- **聚合只有优化类算法**：FedAvg、FedAvgM、FedAdagrad、FedYogi、FedAdam、SCAFFOLD，没有任何鲁棒聚合。FedLLM-Attack 在同一个 `global_aggregate()` 里用 `elif` 补了 Median、Krum、TrimmedMean、FoolsGold、Residual、DnC。
- **数据划分只有 IID**：需要自己补 Dirichlet 划分和自然划分。
- **不保存每轮每个客户端的 LoRA**：`local_dict_list` 每轮都会被覆盖。
- **上传的是 LoRA 的当前值，不是变化量**：因为所有客户端从同一个全局值出发，"平均当前值"等价于"全局值 + 平均变化量"，检测时需要自己减去全局值才能得到更新量。

## 2. Flower（1.40）源码结构

### 2.1 与我们相关的部分

```text
flwr/
├── clientapp/
│   ├── client_app.py        # ClientApp：用 @app.train() 注册训练函数，可以挂 mods
│   └── mod/                 # 内置 Mods：中心化 DP 裁剪、本地 DP、消息大小统计
├── serverapp/
│   ├── server_app.py        # ServerApp：@app.main() 入口
│   └── strategy/
│       ├── strategy.py      # Strategy 基类，start() 就是每轮主循环
│       ├── fedavg.py        # configure_train / aggregate_train / configure_evaluate / aggregate_evaluate
│       ├── krum.py, multikrum.py, bulyan.py, fedmedian.py, fedtrimmedavg.py   # 内置鲁棒聚合
│       └── dp_fixed_clipping.py, dp_adaptive_clipping.py                      # 包装器模式的范例
├── client/mod/secure_aggregation/     # SecAgg / SecAgg+（旧版 API 位置）
└── server/workflow/secure_aggregation/
```

FlowerTune 示例（`examples/flowertune-llm`）只有 4 个文件：
- `client_app.py`：加载分区数据 → 装入全局 LoRA → `SFTTrainer` 训练 → 回传 LoRA 和 `train_loss`、`num-examples`；
- `server_app.py`：初始化 LoRA → `FedAvg.start()`；
- `dataset.py`：用 `flwr_datasets` 的 `IidPartitioner` 划分数据；
- `models.py`：模型加载（默认 4-bit 量化，LoRA r=32）。

### 2.2 一轮流程（`Strategy.start()`）

```text
for 每一轮:
  configure_train(轮次, 全局参数, 配置, grid)   → 抽样节点，构造下发消息
  grid.send_and_receive(...)                    → 客户端执行 [mods → train()]，返回回复消息
  aggregate_train(轮次, 回复列表)               → 聚合，得到新的全局参数
  configure_evaluate / aggregate_evaluate       → 客户端侧评测（可选）
  evaluate_fn(轮次, 全局参数)                   → 服务器侧集中评测（可选）
```

### 2.3 三个关键工程事实

1. **Mod 只能看到消息，看不到数据和训练过程。** Mod 包裹在 `train()` 外面，能拿到的是"下发的全局参数"和"要回传的本地参数与指标"。所以数据检测（H1）和训练中检测（H2）必须写进 `train()` 函数内部，例如包装 `load_data()`、给 `SFTTrainer` 加 `TrainerCallback`。Mod 适合做 H3（上传前）和 H7（收到全局模型后）。
2. **回复格式有硬性要求**：`validate_message_reply_consistency()`（`strategy_utils.py:189`）要求每个回复**恰好一个 ArrayRecord 和一个 MetricRecord**，且所有客户端的键必须一致。客户端的检测摘要要么以固定键名写进同一个 MetricRecord，要么另放一个 ConfigRecord（校验不检查 ConfigRecord）。
3. **包装器模式是官方范式**：DP 策略是 `DifferentialPrivacyFixedClippingBase(strategy=内层策略, ...)`，先对回复做处理，再交给内层策略聚合。我们的服务器侧防御也应该做成这样的包装器：`GuardStrategy(strategy=FedAvg(...))`。这样可以和任何内置聚合组合，Krum、中位数这些基线也就能直接对比。

补充：Flower 1.40 新 API（`flwr.clientapp.mod`、`flwr.serverapp.strategy`）没有导出 SecAgg；SecAgg+ 仍在旧 API 路径 `flwr.client.mod`、`flwr.server.workflow` 下。如果要做"安全聚合与检测共存"，需要确认两套 API 能否混用，这一点尚未核实。

## 3. 防御面矩阵：维度整理

把之前讨论过的维度整理成三组正交的轴。**威胁轴和系统轴是实验配置，防御轴是我们设计的模块属性。**

### 3.1 威胁轴（实验者设定，防御方不知道）

| 轴 | 取值 |
|---|---|
| T1 攻击者角色 | 无 / 恶意客户端 / 被污染的诚实客户端 / 不可信服务器 |
| T2 攻击对象 | 数据 / 更新 |
| T3 攻击目标 | 安全对齐破坏 / 无害触发器后门 / 通用能力破坏 |
| T4 时间模式 | 单轮 / 连续 / 周期 / 随机间歇 / 前期攻击后停止 |
| T5 规模与协作 | 1 个 / 多个独立 / 多个协同 |
| T6 污染浓度 | 单客户端内的污染比例，以及污染分布在多少个客户端上 |

### 3.2 系统轴（防御方知道）

| 轴 | 取值 | 影响 |
|---|---|---|
| S1 参与方式 | 全员 / 按比例抽样 | 抽样会让历史参照不连续 |
| S2 数据分布 | IID / Dirichlet / 自然划分 | 决定良性差异有多大 |
| S3 PEFT 形式 | LoRA / 冻结 A 的 FFA-LoRA | 影响 A、B、BA 特征的意义 |
| S4 基础聚合 | FedAvg / FedAdam / … | 影响更新的尺度 |
| S5 隐私机制 | 无 / SecAgg / DP | **SecAgg 会让服务器侧逐客户端检测全部失效** |
| S6 模型规模 | 0.5B / 1.5B / 7B | 算力与迁移性 |

### 3.3 防御轴（模块属性）

| 轴 | 取值 |
|---|---|
| D1 挂载点 | H1 数据入库 / H2 训练中 / H3 上传前 / H4 接收后 / H5 聚合时 / H6 试合并 / H7 收到全局模型后 / H8 训练结束 |
| D2 观察权限 | O0 本地数据 / O1 元数据与自报统计 / O2 逐客户端更新 / O3 可对模型做探针 / O4 可信执行环境内 / O5 只有全局模型 |
| D3 可信等级 | L0 自报 / L1 承诺抽查 / L2 可信执行环境（只对客户端侧插件有意义） |
| D4 观察对象 | 文本 / 逐样本梯度 / A / B / BA / 激活 / 输出 / 参与记录 |
| D5 参照 | 同轮横向 / 自身历史 / 可信参照 |
| D6 判定粒度 | 样本 / 客户端-轮次 / 客户端 / 簇 / 整轮 |
| D7 处置 | 标记 / 降权 / 剔除 / 回滚 |

### 3.4 轴之间的约束（设计时必须遵守）

- **D1 决定 D2**：H1–H3、H7 在客户端，最高权限 O0；H4–H6、H8 在服务器，最高权限 O2 或 O3。服务器侧插件**绝不能**拿到原始数据。
- **S5=SecAgg 时**，H4–H6 只能看到聚合和，逐客户端检测要移到客户端（H3）或可信执行环境（O4）。
- **S1=抽样时**，D5 的"自身历史"要改成"与上次参与时比较"。
- **T1=不可信服务器时**，只有 H7 有效。

## 4. 注入点对照表

| 挂载点 | OpenFedLLM / FedLLM-Attack 中的位置 | Flower 中的位置 | 插件拿到的输入 |
|---|---|---|---|
| H1 数据入库 | `main_sft.py` 划分数据之后，对每个 `local_datasets[i]` 过滤 | `train()` 中包装 `load_data()` 的返回值 | 本地样本 |
| H2 训练中 | 在 `get_fed_local_sft_trainer()` 返回的 trainer 上 `add_callback()` | 同样在 `train()` 里给 `SFTTrainer` 加 callback | 每步 loss、梯度 |
| H3 上传前 | `trainer.train()` 之后、`local_dict_list[client] = ...` 之前（FedLLM-Attack `main_sft.py:109-116`） | 客户端 Mod：`call_next()` 返回之后 | 本地 LoRA、下发的全局 LoRA |
| H7 收到全局模型后 | 每个客户端循环开头 `set_peft_model_state_dict(model, global_dict)` 之后（`main_sft.py:88`） | 客户端 Mod：`call_next()` 之前 | 全局 LoRA、本地探针集 |
| H4 接收后 | `global_aggregate()` 调用之前 | `GuardStrategy.aggregate_train()` 开头 | 各客户端 LoRA、自报指标、节点 ID |
| H5 聚合时 | 在 `global_aggregate()` 中新增 `fed_alg='guard'` 分支，或者先过滤 `clients_this_round`、调整 `sample_num_list` 再调用 | 过滤或重新加权回复后，调用 `self.strategy.aggregate_train()` | 风险分数、可信度 |
| H6 试合并 | 聚合前用共享的 `model` 临时装入候选 LoRA 做探针评测 | 在 `aggregate_train()` 中加载模型做探针评测（需要服务器有 GPU） | 候选 LoRA、可信探针集 |
| H8 训练结束 | 主循环之后 | `evaluate_fn` 或 `start()` 返回之后 | 最终模型、全部记录 |
| 记录层 | H3 之后，按"轮次/客户端"落盘 | `aggregate_train()` 中落盘 | — |

**Flower 中的一个现成范例**：`fixedclipping_mod`（`clientapp/mod/centraldp_mods.py:44`）先保存下发的参数，再调用 `call_next()` 训练，然后对"回传值 − 下发值"做处理。这恰好就是 H7 + H3 所需的结构，可以直接照着写。

## 5. 核心库接口草案

与框架无关的核心库只定义数据和插件；两个适配器负责在上表的位置调用插件。

```python
@dataclass
class ClientUpdate:              # 服务器侧插件能看到的全部内容（O2）
    client_id: str
    round: int
    lora: dict[str, Tensor]      # 本轮上传的 A/B
    base: dict[str, Tensor]      # 本轮下发的全局 A/B（用于算更新量）
    reported: dict[str, float]   # 客户端自报：样本数、loss、检测摘要
    trust_level: str             # "L0" | "L1" | "L2"

class Plugin(Protocol):
    hook: str                    # "H1" … "H8"
    permission: str              # "O0" … "O5"，适配器据此决定传入什么
    def run(self, inputs, state) -> "Findings": ...

@dataclass
class Findings:
    scores: dict[str, float]     # 按样本 / 客户端 / 簇给出的风险分数
    evidence: dict               # 可解释的中间量，写入记录层
```

**关键设计**：适配器按 `permission` 构造输入。例如 O2 插件只收到 `list[ClientUpdate]`，拿不到数据集对象。这样即使在 OpenFedLLM 的单进程模拟里，也能保证服务器侧插件"看不到数据"，实验结论才能迁移到真实部署。**真值标签**（谁是恶意客户端、哪些样本被污染）只交给评测模块，不进入任何插件。

判定引擎（良性基线校准 → 多视角融合 → 可信度累积 → 分级处置）作为 H5 的一个特殊插件，读取 H3、H4、H6 的 Findings。

## 6. 建议的实施顺序

| 步骤 | 内容 | 平台 |
|---|---|---|
| 1 | 核心库：`ClientUpdate`、`Plugin`、`Findings`、记录层 | 与框架无关 |
| 2 | OpenFedLLM 适配器：在 H3、H4、H5 三处接入；先跑一个"只记录、不处置"的插件，验证每轮 A/B 都正确落盘 | FedLLM-Attack 分支 |
| 3 | H4 特征插件：A/B/BA 特征（方向 A） | 同上 |
| 4 | 补 Dirichlet 划分；跑 S0（无攻击）得到良性基线 | 同上 |
| 5 | H6 试合并插件 + 判定引擎，跑 S1 | 同上 |
| 6 | Flower 适配器：`GuardStrategy` 包装器 + 客户端 Mod（H3、H7）+ `train()` 内的 H1/H2 钩子 | Flower |
| 7 | 用同一批插件在 Flower 的多节点模式下演示 | Flower |

第 2 步是整个工作的地基：只有逐轮逐客户端的记录可靠，后面的特征、基线和判定才有意义。
