# 第 1 部分：方向 A 的原理

## 1.1 先回顾 LoRA 在做什么

模型中的一个线性层有一个大矩阵 W（例如 4096×4096，约 1677 万个参数）。LoRA 冻结 W，只训练两个小矩阵：

```text
新权重 W' = W + ΔW,   ΔW = B · A
B: d × r   (4096 × 16)
A: r × k   (16 × 4096)
```

r（秩）很小，通常取 8–32。所以每层只需训练和上传约 13 万个参数，而不是 1677 万。

**关键点：真正改变模型行为的是乘积 ΔW = BA，而不是 A 或 B 单独的值。**

## 1.2 现在的服务器在检查什么

在 OpenFedLLM 这类框架里，服务器收到每个客户端的 A、B 后：

1. **聚合**：把所有客户端的 A 平均一次，所有 B 平均一次；
2. **检测**（如果有）：把 A、B 拉平成长向量，计算范数、余弦相似度，或者做聚类。

也就是说，**检测和聚合的对象都是 A、B，而不是 BA**。这会带来两个问题。

## 1.3 问题一：同一个效果可以有无数种写法

任取一个可逆的 r×r 矩阵 M，令

```text
B' = B · M,   A' = M⁻¹ · A
则 B'A' = B · M · M⁻¹ · A = BA
```

模型效果**完全不变**，但 A、B 的数值可以变得面目全非。

**最简单的例子（r=1）**：把 B 乘 10，A 除以 10，乘积不变，但 B 的范数变成原来的 10 倍，A 变成 1/10。

数值验证结果：用随机 M 变换后，BA 完全相同，而 A 的范数从 55.6 变为 241.0，B 从 63.9 变为 167.2。

**对防御的含义**：只看 A、B 统计量的检测器，看到的是"表面写法"而非"实际效果"。这会导致两类错误：

- **误报**：一个良性客户端因为优化路径或初始化不同，A、B 的数值偏离其他客户端，但效果正常，却被判为异常；
- **漏报**：一个 A、B 数值看起来正常的更新，乘积的效果却可能异常。2026 年的 GAP 论文就指出了这一盲区（服务器从不验证乘积）。

## 1.4 问题二：分开平均 ≠ 效果的平均

两个客户端时：

```text
服务器实际得到:  ((B₁+B₂)/2) · ((A₁+A₂)/2) = (B₁A₁ + B₁A₂ + B₂A₁ + B₂A₂) / 4
理想的效果平均:  (B₁A₁ + B₂A₂) / 2
```

前者多出了交叉项 B₁A₂、B₂A₁，也就是"客户端 1 的 B 配上客户端 2 的 A"，它们不对应任何客户端真正训练出来的东西。数值验证中两者的相对偏差约为 70%（随机矩阵下偏差偏大；真实训练中客户端从同一起点出发，偏差通常会小一些，具体多大需要实测）。

这个现象在 FFA-LoRA、FLoRA 等工作中被当作**精度问题**讨论过。我们关心的是一个新问题：**这种偏差会不会让攻击效果在聚合时被放大或掩盖？防御方能否利用它？**

## 1.5 方向 A 的核心：直接在"效果"上做检测

最直接的办法是把每个客户端的 BA 算出来再检测，但代价很高：7B 模型每个客户端每轮要展开几十个 4096×4096 矩阵，10 个客户端就是上百亿次浮点运算和几 GB 内存。

**数学技巧：检测所需的统计量都能在 r×r 的小空间里精确算出，不需要展开大矩阵。**

| 需要的统计量 | 直接算（大矩阵） | 等价的小矩阵算法 | 验证 |
|---|---|---|---|
| 效果大小 ‖BA‖² | 展开 d×k | tr( (BᵀB) · (AAᵀ) )，两个都是 r×r | ✓ 完全一致 |
| 两个客户端效果的相似度 ⟨B₁A₁, B₂A₂⟩ | 展开两个 d×k | tr( (B₁ᵀB₂) · (A₂A₁ᵀ) )，都是 r×r | ✓ 完全一致 |
| 效果的"形状"（奇异值谱） | 对 d×k 做 SVD | B=Q₁R₁，Aᵀ=Q₂R₂，只对 R₁R₂ᵀ（r×r）做 SVD | ✓ 完全一致 |

有了内积，就能算余弦相似度 = ⟨ΔW₁,ΔW₂⟩ / (‖ΔW₁‖·‖ΔW₂‖)。于是现有基于距离或相似度的检测方法（Krum、FoolsGold、聚类等）都可以**原样换到效果空间**上运行。

**这些统计量不受写法变化影响。** 把 B→BM、A→M⁻¹A 代入，BᵀB 和 AAᵀ 的变化恰好相互抵消，迹不变。所以效果层的特征天然回避了 1.3 节的问题。这是方向 A 在理论上成立的核心理由。

用直观的比喻：现在的检测是在比对两份配方的"写法"，同一道菜可以写成无数种配方；方向 A 是直接比对"做出来的菜"，而且找到了一种不用真的把菜做出来就能尝味道的方法。

## 1.6 方向 A 要回答的研究问题（还没有答案）

| 问题 | 为什么重要 | 实验对照 |
|---|---|---|
| Q1：效果层特征比因子层特征检测得更准吗？ | 核心卖点 | 同一检测器，输入分别用因子特征和效果特征 |
| Q2：它能降低自然 non-IID 下的良性误杀吗？ | 对应 1.3 节的"误报" | 在 FedLLM-Bench 自然划分上比较良性客户端的误杀率 |
| Q3：分开平均的偏差和攻击有无关系？ | 1.4 节的新问题 | 测量有/无攻击时交叉项占比的差异 |
| Q4：计算开销是否真的可以忽略？ | 平台"轻量级"的定位 | 记录每轮检测耗时与显存 |
| Q5：冻结 A 的变体（FFA-LoRA）是否让问题消失？ | 天然的消融对照：A 固定时交叉项消失，写法歧义也大幅减少 | 同一实验在 FFA-LoRA 下重跑 |

**需要诚实面对的局限**：

- 如果现有攻击基线产生的 A、B 本身就很异常，两类特征都能检出，差异就体现不出来。所以需要加一组"对因子做写法归一化"的压力测试。这只是对上传值做 1.3 节的等价变换，**不改变攻击目标，也不引入新攻击**，用来检验检测器是否依赖写法。
- 效果层特征仍然是统计量。如果攻击的效果大小和方向都接近良性更新，只看统计量不够。所以方向 A 必须和行为层检测配合，这也是第 2 部分采用完整流程的原因。

# 第 2 部分：服务器阶段的完整攻防实验流程

## 2.1 总体架构：五层

```text
┌────────────────────────────────────────────────────────────┐
│ ⑤ 记录层：每轮保存 A/B、检测分数、聚合权重、行为指标        │
├────────────────────────────────────────────────────────────┤
│ ④ 评测层：能力、安全、后门触发、检测指标、持久性             │
├────────────────────────────────────────────────────────────┤
│ ③ 防御层：D1 数据侧 → D2 更新侧 → D3 聚合 → D4 行为 → D5 修复 │
├────────────────────────────────────────────────────────────┤
│ ② 联邦训练层：OpenFedLLM / FedLLM-Attack（LoRA, FedAvg）    │
├────────────────────────────────────────────────────────────┤
│ ① 威胁模拟层：S0–S5 场景，只用公开基线与无害触发器           │
└────────────────────────────────────────────────────────────┘
```

**一轮的执行流程**：

```text
服务器下发全局 LoRA
  → 各客户端：[D1 本地数据审查] → 本地训练 → 上传 A,B
  → 服务器：[D2 更新检测：因子特征 + 效果特征(方向A)] → 风险分数
  → [D3 聚合：按风险/可信度调整权重，或剔除]
  → 得到新的全局模型 → [D4 行为探针，每 N 轮一次]
  → 记录层写入本轮所有数据
训练结束 → [D5 事后修复（可选）] → 最终评测 → 攻击停止后继续训练，看持久性
```

## 2.2 威胁场景矩阵（S0–S5）

| 编号 | 场景 | 谁是攻击者 | 使用的公开基线 | 主要考验的防御层 |
|---|---|---|---|---|
| S0 | 无攻击（含自然 non-IID） | 无 | FedLLM-Bench / 常规指令数据 | 测**误杀率**，所有防御都必须跑 |
| S1 | 恶意客户端数据投毒 | 少数客户端 | FedLLM-Attack 的数据（安全对齐破坏） | D2、D3、D4 |
| S2 | 诚实客户端被分散低浓度污染 | 无恶意客户端，数据源被污染 | ProtegoFed / Signal Aggregation 设置 + 无害触发器 | D1（D2 预计较弱） |
| S3 | 更新层扰动 | 少数客户端 | FLPoison 中的 ALIE、Min-Max 等（按 LoRA 向量应用） | D2、D3 |
| S4 | 知道防御存在的攻击者 | 少数客户端 | 对 S1/S3 的上传值做写法归一化（1.6 节） | D2 效果层 vs 因子层 |
| S5 | 服务器不可信 | 服务器 | 暂不实现，只在平台中预留客户端侧验证接口 | 客户端侧 D4 |

**时间模式**（在 S1–S3 上正交组合）：连续攻击 / 周期性参与 / 随机间歇 / 只在前期攻击然后停止（用来测持久性）。

**无害触发器约定**：后门目标统一为"回答中出现固定标记词"之类的可观测、无害行为。安全对齐类实验只使用 FedLLM-Attack 公开数据，攻击数据不外传。

## 2.3 防御层 D1–D5 与平台模块对应

| 层 | 内容 | 基线 | 我们的方法 | 对应立项报告模块 |
|---|---|---|---|---|
| D1 数据侧 | 客户端本地样本审查 | 规则 + 安全分类器；ProtegoFed | 跨轮增量清洗（方向 C） | 文本多层异常检测 |
| D2 更新侧 | 对上传的 LoRA 打风险分数 | 范数、余弦、Safe-FedLLM、Horus | **效果层特征（方向 A）** + 跨轮历史 | 提交方动态可信度 |
| D3 聚合 | 按风险调整权重 | FedAvg、Krum、Median、Trimmed Mean、FoolsGold | 可信度加权；可信子空间投影（方向 B） | 聚合前过滤 |
| D4 行为 | 全局模型的安全和触发探针 | 固定安全测试集 + judge | 每 N 轮抽检，异常时回溯 D2 记录 | 可视化告警 |
| D5 修复 | 事后恢复 | FedLLM-Attack 的 post-hoc 防御、回滚 | 利用记录层回滚到可疑轮次之前 | 溯源 |

**实验原则**：每一层都要能单独开关，才能做消融实验（只开 D2、D1+D2、全开……）。

## 2.4 评测指标

| 类别 | 指标 | 说明 |
|---|---|---|
| 能力 | MT-Bench / 任务准确率 / helpfulness 评分 | 防御不能以牺牲能力为代价 |
| 安全 | 有害请求拒答率、违规率 | S1 主指标 |
| 后门 | 带触发 ASR、不带触发的误触发率 | S2 主指标 |
| 检测 | 客户端-轮次级 TPR / FPR / AUPRC，样本级 Recall / FPR | S0 下的 FPR 尤其重要 |
| 公平 | 被误杀良性客户端的最差效用 | 对应自然 non-IID |
| 时间 | 检测延迟（第几轮发现）、Persistence@k（停止攻击 k 轮后残留） | 跨轮研究 |
| 开销 | 每轮检测耗时、额外显存 | 验证"轻量级" |

## 2.5 服务器配置与规模估计

**模型**：Qwen2.5-7B-Instruct 或 Llama-3.1-8B-Instruct（选一个作为主模型，另一个用于迁移验证）；用 Qwen2.5-0.5B/1.5B 快速扫参数。

**显卡**：推荐单卡 A100/H100 80GB，或 L40S/A6000 48GB。多个客户端在同一张卡上按顺序模拟即可，不需要多卡并行。FedLLM-Attack 默认 8-bit 加载 + LoRA，48GB 已经比较宽裕。

**记录层磁盘估算**（以 7B、rank 32、q_proj + v_proj、32 层为例）：
每个客户端每轮的 A+B ≈ 64 个模块 × 26 万参数 ≈ 1680 万参数 ≈ 33.5 MB（bf16）。
10 个客户端 × 100 轮 ≈ **33.5 GB/次实验**。实验次数多时，只保留效果层的 r×r 统计量，再抽样保留完整因子。

**实验量控制**（防止组合爆炸）：

| 阶段 | 模型 | 内容 | 目的 |
|---|---|---|---|
| P1 | 0.5B/1.5B | S0、S1 × 全部防御 × 3 个种子，轮数较少 | 跑通流程，筛选方法 |
| P2 | 7B | S0、S1、S2 × 主要防御 | 主结果 |
| P3 | 7B | S3、S4、时间模式、持久性 | 鲁棒性和创新点验证 |
| P4 | 另一个 7B 或 8B | 选取的关键设置 | 迁移验证 |

具体耗时需要在 P1 实测后再排 P2–P4，不要事先拍定。

## 2.6 代码组织建议

在 OpenFedLLM 的"本地训练结束 → 聚合"之间插入统一接口，使每层防御都能插拔：

```text
defense/
  data_side.py      # D1: filter(samples) -> kept_samples, scores
  update_side.py    # D2: score(client_AB_list, history) -> risk[i]
    ├ factor_features()   # 基线：因子层
    └ effect_features()   # 方向A：r×r 空间下的范数/内积/谱
  aggregate.py      # D3: weights = f(risk, trust); new_global = agg(...)
  behavior.py       # D4: probe(global_model) -> safety/asr
  repair.py         # D5
threats/            # S1–S4 配置，只引用公开数据和基线
logging/            # 记录层：每轮统计量、可信度、聚合权重
eval/               # 统一评测脚本（固定 prompt 模板和 judge）
```

**记录层是整套平台的地基**：D4 发现异常后要回溯 D2，D5 回滚要用历史记录，平台的可视化也要读这些数据，所以第一版就应该实现。

## 2.7 实施顺序

1. P1 小模型跑通 S0 + S1、无防御，确认攻击能从数据传到更新再传到行为（这是后面所有工作的前提）。
2. 实现记录层，并实现 D2 的两类特征（因子层、效果层），离线比较 Q1。
3. 接入 D3 基线聚合和 D4 行为探针，完成第一张"场景 × 防御"结果表。
4. 上 7B，补 S2（与 ProtegoFed 对比）和 S0 自然 non-IID 误杀测试（Q2）。
5. 做 S4 写法归一化压力测试和 FFA-LoRA 消融（Q5）。
6. 在结果稳定后再接平台界面和 D5。
