# 可信客户端检测与嵌入式防御模块设计

> 整理日期：2026-09-26
> 回答三个问题：① 客户端能否可信地做数据分析？② 能否做一个嵌入训练流程、覆盖安全测试矩阵的检测模块？③ 开源联邦 LLM 平台的能力边界在哪里，产品应基于哪个平台？
> 证据状态：NVFlare Filters、NVFlare 机密计算、Flower Mods 已查阅官方文档；FATE-LLM、FederatedScope-LLM、FedML 只核对了检索摘要，选型前需再看仓库的维护状态。

---

## 1. 客户端能否可信地做数据分析？

**答案取决于威胁模型。**

| 场景 | 客户端检测是否可信 | 原因 |
|---|---|---|
| 诚实客户端 + 数据源被污染（S2） | **可信** | 客户端本身也希望模型干净，会认真执行检测，只是缺少工具 |
| 恶意客户端（S1、S3） | **单靠软件不可信** | 检测跑在对方的机器上，对方可以不执行，或者伪造报告 |

所以客户端模块在 S2 场景下可以直接成为主力防御。对恶意客户端，要让服务器"相信客户端的检测确实执行了"，有以下几级手段：

| 可信等级 | 手段 | 服务器能相信什么 | 成本与局限 |
|---|---|---|---|
| **L0 自报** | 客户端上报检测摘要（如风险样本比例） | 什么都不能完全相信，只能与服务器侧证据交叉核对 | 零成本 |
| **L1 承诺 + 抽查** | 训练前提交数据集哈希（Merkle 根）；服务器随机抽查少量样本，或要求重放某一步训练并比对结果（思路见 Proof-of-Learning, Jia 等, IEEE S&P 2021） | "数据在训练前已固定，抽查部分与声明一致" | 抽查会暴露少量样本，隐私上有代价；重放需要额外计算 |
| **L2 可信执行环境** | 数据检测和训练都在带远程证明的机密虚拟机中运行（CPU: AMD SEV-SNP / Intel TDX；GPU: H100 CC 模式） | "这个更新确实由指定代码、在通过指定检测的数据上训练得到" | 需要支持机密计算的硬件；NVFlare 已有官方方案 |
| L3 密码学证明 | 对训练过程生成零知识证明 | 最强 | 对 LLM 训练目前不现实 |

**对项目的启发（可作为一个创新点）**：把可信等级作为证据写入第 5 节的动态可信度。例如 L2 客户端的更新默认权重更高，L0 客户端要经过更严格的服务器侧检测。这就是"**可信等级感知的聚合**"。

**关于安全聚合（SecAgg）的冲突**：开启 SecAgg 后，服务器只能看到聚合和，看不到单个客户端的更新，服务器侧的 LoRA 检测会全部失效。所以产品需要二选一，或者把检测移到客户端和可信执行环境里。这个取舍应该在产品设计中明确写出来。

## 2. 嵌入式检测模块：挂载点设计

模块不需要重写训练框架，只需在训练生命周期的固定位置挂载检测插件：

| 编号 | 挂载点 | 位置 | 能拿到的信息 | 适合的检测 |
|---|---|---|---|---|
| H1 | 数据入库 | 客户端 | 原始样本 | 文本安全分类、嵌入离群、困惑度、近重复 |
| H2 | 训练中（每步） | 客户端 | 逐样本 loss、梯度 | 训练动态、逐样本梯度聚类（ProtegoFed 类） |
| H3 | 上传前 | 客户端 | 本轮本地 LoRA | 客户端自检、生成检测摘要或证明 |
| H4 | 接收后 | 服务器 | 各客户端 A/B、自报统计 | A/B/BA 特征、跨轮历史 |
| H5 | 聚合时 | 服务器 | H4 的风险分数 + 可信度 | 鲁棒聚合、降权、剔除 |
| H6 | 试合并 | 服务器 | 候选全局模型 | 验证集贡献、拒答方向投影、簇级行为验证 |
| H7 | 下发后 | 客户端 | 收到的全局模型 | 客户端侧行为验证（应对服务器不可信） |
| H8 | 训练结束 | 服务器 | 最终模型 + 全部记录 | 完整安全评测、溯源、回滚 |

**各威胁场景由哪些挂载点覆盖：**

| 场景 | 主要挂载点 | 盲区（产品必须如实标注） |
|---|---|---|
| S0 无攻击 | 全部（用于测误报率） | — |
| S1 恶意客户端数据投毒 | H4、H5、H6、H8 | 客户端侧 H1–H3 不可信（除非达到 L1/L2） |
| S2 诚实客户端被污染 | H1、H2、H3 | 服务器侧基本看不到 |
| S3 更新层扰动 | H4、H5、H6 | 统计特征贴近良性时，要靠 H6 |
| S4 知道防御的攻击者 | H4（效果层）、H6 | 探针覆盖不到的行为 |
| S5 服务器不可信 | H7 | 需要多个客户端协同验证 |

**关于"覆盖全部"**：模块能做到的是**每个威胁场景至少有一个观察点**，而不是**能发现所有攻击**。比如行为探针无法枚举未知的触发条件，开启 SecAgg 时 H4 不存在。产品和论文都应该给出这张覆盖表，并明确标注盲区。这比宣称"全面防护"更可信，评审也更认可。

## 3. 开源联邦 LLM 平台的能力边界

| 平台 | 定位 | 有什么 | 缺什么 | 对我们的用途 |
|---|---|---|---|---|
| **OpenFedLLM / FedLLM-Attack** | 研究模拟 | LoRA 联邦 SFT/DPO；内置 Krum、Median、TrimmedMean、FoolsGold、DnC；FedLLM-Attack 的攻击和评测 | 单进程模拟，没有真实通信；没有客户端挂载点；不保存每轮更新 | **算法实验主平台**（复用已有基线） |
| **Flower / FlowerTune** | 研究 + 部署 | 真实客户端-服务器通信，也有模拟引擎；客户端 **Mods**（包裹 ClientApp，可检查和修改收发消息）；服务器 **Strategy**（可自定义聚合，自带 Krum、中位数等）；SecAgg+、差分隐私；FlowerTune LLM 基准 | 没有面向 LLM 的投毒检测；没有行为探针和审计 | **产品原型首选**：Mods 对应 H1–H3、H7，Strategy 对应 H4–H6 |
| **NVIDIA FLARE** | 工业级 | 客户端和服务器两侧都有 **Filters**（可在任务下发和结果回传时处理数据）；支持 HF Trainer / TRL；同态加密、差分隐私；**机密计算**（SEV-SNP + H100/Blackwell，带远程证明） | 部署较重；同样没有 LLM 投毒检测 | 需要 L2 可信等级时的平台；Filters 也是天然的挂载点 |
| FATE-LLM | 工业级（国内生态） | 多种 PEFT、同构和异构模型、隐私保护 | 部署重，二次开发门槛高 | 暂不建议 |
| FederatedScope-LLM | 研究 | 多种 FedPEFT 算法和基准 | 维护状态需确认 | 参考其算法实现 |
| FedML FedLLM | MLOps 平台 | 与 HF、DeepSpeed 兼容 | 偏商业托管 | 暂不建议 |

**共同的空白**：这些平台最多提供**传统鲁棒聚合**（Krum、中位数这一类），都没有：
- 面向文本数据的安全检测；
- LoRA 专用的效果层分析；
- 行为探针和簇级验证；
- 可信度档案、审计日志和溯源回滚；
- 与 SecAgg、可信执行环境配套的检测位置设计。

**这就是软件产品的定位**：做一个可以插进现有联邦平台的**安全检测层**，而不是再做一个联邦训练平台。

## 4. 推荐的产品架构

```text
┌──────────────────── 可视化与审计（读取日志） ────────────────────┐
├──────────────────── 核心库（与框架无关） ─────────────────────────┤
│  插件接口：每个检测算法声明 {挂载点 H1–H8, 所需权限 O0–O5, 输出}   │
│  特征库：A/B/BA 效果特征、文本特征、行为探针                       │
│  判定引擎：良性基线校准 → 多视角融合 → 可信度累积 → 分级处置        │
│  可信等级：L0 自报 / L1 承诺抽查 / L2 可信执行环境证明              │
│  记录层：每轮每客户端的特征、分数、权重、处置                       │
│  测试矩阵运行器：按配置批量运行 S0–S5 × 时间模式 × 参与方式          │
├──────────────────── 适配层 ─────────────────────────────────────┤
│  OpenFedLLM 适配器（实验）  Flower 适配器（产品）  NVFlare 适配器（可选） │
└─────────────────────────────────────────────────────────────────┘
```

**分工建议**：
1. 核心库先在 OpenFedLLM 上跑实验，复用 FedLLM-Attack 的基线和评测，尽快出算法结果。
2. 同一套核心库通过 Flower 适配器做产品原型：客户端 Mod + 服务器 Strategy，可以真实多机演示。
3. 如果租到支持机密计算的 H100，再考虑 NVFlare 适配器，演示 L2 可信等级。

**注意**：插件接口里的"所需权限"字段必须被强制检查。例如服务器侧插件不能读取原始数据，这样模拟实验的结论才能迁移到真实部署。

## 5. 算法迁移创新怎样做

插件接口让"迁移"变得系统化：把一个已有方法迁移过来时，必须回答三个问题。①它挂在哪个挂载点？②需要什么权限？③在 LoRA 上的特征怎么定义（A、B 还是 BA）？然后在同一个测试矩阵上评测。

| 原方法 | 原场景 | 迁移后 | 需要解决的新问题 |
|---|---|---|---|
| FLTrust | 视觉 FL，服务器持有可信数据 | H4/H5，在 BA 效果空间计算与可信参照的相似度 | 可信数据覆盖不到的领域怎样避免误杀 |
| FLDetector | 视觉 FL，跨轮预测一致性 | H4，随机抽样参与下的历史预测 | 客户端历史不连续 |
| FoolsGold | 视觉 FL，Sybil 相似度 | H4/H5，在 BA 空间计算相似度，并结合领域元数据 | 良性同领域客户端本来就相似 |
| Activation Clustering | 集中式分类后门检测 | H6，对簇试合并后的激活做聚类 | 生成式模型该选哪一层、哪个 token 位置 |
| ONION | 集中式文本后门 | H1，客户端数据清洗 | 指令数据中的长文本与对话格式 |
| Spectral Signatures | 集中式 | H2，逐样本 LoRA 梯度谱分析 | 与 ProtegoFed 的比较与互补 |

**可以宣称的创新**：
1. LoRA 效果层特征（方向 A）；
2. 可信等级感知的聚合；
3. 统一的挂载点和权限模型，以及在同一矩阵上的系统迁移评测。

其中第 3 点既是产品的核心，也是一项可发表的实证工作。
