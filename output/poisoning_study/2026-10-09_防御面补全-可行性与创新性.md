# 把防御面做全：可行性与创新性分析（2026-10-09）

> 范围：只看防御，攻击模拟不在本文内。
> 依据：137 张精读卡片、昨天的开放性检查（47 篇防御与检测论文的归类）、今天对 HF 和 Flower 接口的最小探查，以及三次补充检索。
> 没有做训练实验。探查用的是 2 层、隐藏维 32 的随机小模型，只说明接口能不能用，不说明开销。

## 0. 结论

1. **可行。** 补全需要六项改动，其中四项的关键接口今天探查通过，两项在接口上看可行但没有运行验证。没有发现需要改上游框架才能做的事。
2. **做完后覆盖面的估计：47 篇里约 39 篇有落点**（现在是 21 篇）。剩下约 8 篇要改损失函数、在推理时起作用、或者依赖密码学和聚合协议，仍然进不来。这是按机制作的估计，要靠逐篇移植来验证。
3. **创新点是系统层面的，不是算法层面的。** 在我查到的范围内，没有一个现有平台同时具备：两侧统一的挂载位置、插件对数据的显式声明、针对 LoRA 的对象、两侧可对照的记录。
4. **昨天平台调研里有一处要更正。** "逐轮记录并重放没有先例"不成立：FedDebug（ICSE 2023）已经用记录与重放做联邦学习的调试。记录与重放本身不能算创新点。
5. **最大的风险在开销。** 逐样本梯度一类的方法，按我的估算在我们的设置下每个客户端要多花约 100 秒，是一轮本地训练的十几倍。接口可以提供，但"低开销"只对采集底座成立，对这类插件不成立，文档里必须分开说。

## 1. "做全"指什么

按防御起作用的位置，把文献里的防御分成八类。括号里是 47 篇中的篇数，一篇只归入它主要起作用的一类。

| 类别 | 位置 | 现在能写 | 代表 |
|---|---|---|---|
| 分发前加固与标记（5） | 服务器，下发前 | 0 | Vaccine、Booster、RepNoise、TAR、EmbTracker |
| 收到模型后的检查（2） | 客户端，训练前 | 2 | PEFTGuard、TriShield 的检测部分 |
| 数据清洗与增补（12） | 客户端，训练前 | 3 | ProtegoFed、GradSentry、谱签名、激活聚类、BEA |
| 训练过程约束（4） | 客户端，训练步 | 0 | Lisa、Obliviate、弱到强蒸馏遗忘、差分隐私 LoRA |
| 更新级检测与稳健聚合（14） | 服务器，收到更新与聚合 | 13 | Krum、FoolsGold、FreqFed、FLTrust、FLAME、FLDetector |
| 行为探针（2） | 服务器或节点，聚合前 | 0 | Chorus、DeepSight |
| 聚合后修复（3） | 服务器，聚合后 | 2 | Safe LoRA、CRFL、Antidote |
| 推理时、密码学与协议（5） | 训练之外 | 1 | STRIP、PSIM、Verifiable Fine-Tuning、FedGT、Proof-of-Learning |

"现在能写"合计 21 篇，对应开放性检查里"能写"的 13 篇和"能写但别扭"的 8 篇。Safe-FedLLM 按它已经能写的客户端级归在"更新级检测"，它的步级部分属于训练过程。可以看到，现在能写的几乎都在"更新级检测与稳健聚合"一类；数据侧、训练过程、行为探针、分发前这四类基本是空的。"做全"就是让这四类也有落点。

## 2. 六项改动的可行性

### 2.1 通用的模型句柄

**做什么**：定义两侧共用的接口，提供 HF 实现。至少四个能力：临时加载一份 LoRA 并精确恢复；前向取指定层的隐藏状态与对数概率；对给定样本取指定参数的逐样本梯度；生成文本。

**探查结果**（随机小模型上）：

| 能力 | 结果 |
|---|---|
| 取隐藏状态与对数概率 | 可用，`output_hidden_states=True` |
| 逐样本梯度 | 逐条循环可用；`torch.func.vmap` 在这个模型上失败（模型内部有依赖数据的控制流），所以只能循环，耗时随样本数线性增长 |
| 生成文本 | 可用 |
| 临时加载后精确恢复 | 逐位恢复；现有 `HFProbe` 已经是这个做法 |
| 取 LoRA 下投影的激活 | 用前向钩子可取到 |

**解开**：GradSentry、GradSafe、谱签名、激活聚类、LoRAScan、影响函数防御、Antidote、DeepSight 共 8 篇；也是 ProtegoFed、CrowdGuard、Chorus 的前提。

**风险**：
- 开销。ProtegoFed 要对每条本地样本单独反传一次。按昨天的实测（5 步、批大小 4，约 6.7 秒，即每条样本前向加反向约 0.33 秒）粗算，300 条样本约 100 秒，是一轮本地训练的十几倍。这是我的估算，没有实测。该方法只在第一轮之前做一次，但仍然是一笔明显的开销。
- 句柄和训练用的是同一个模型对象。插件拿到它之后可以改参数，约定只能靠"用完恢复"来保证，库无法强制。

**判断**：可行，工作量中等，是六项里价值最大的一项。

### 2.2 样本的增补与改写

**做什么**：在客户端训练前增加一个动作，允许插件给出新增的样本或改写后的样本；训练代码改为向客户端采集对象要训练集，而不是直接用原数据集。

**依据**：现有的 `kept_indices()` 已经是"训练代码向采集对象问该用哪些样本"的形态，只是只能减。HF 的数据集支持按下标选取和拼接。

**解开**：BEA、Safety-Tuned LLaMAs；ONION 可以按原方法删词而不是整条删。

**风险**：开启后训练数据变了，训练结果必然不同。这是动作的本意，但要和"采集不改变训练结果"这条承诺分开表述。新增的样本要进清单并标明来源是哪个插件。

**判断**：可行，工作量小。

### 2.3 通道传张量，加训练前的握手

**做什么**：通道除小记录外，允许附带张量，上限可配置；在第一轮训练之前加一次往返。

**探查结果**：Flower 的一条消息里可以放多个数组记录。内置的 FedAvg 在聚合前会校验各回复的记录是否一致，所以适配器必须在交给内层策略之前把附带的张量取走；现有适配器对通道的配置记录已经是这样处理的。训练前的握手在单进程适配器里是直接的函数调用；在 Flower 里需要在训练轮之外多发一轮消息，**这一点我没有验证**。

**解开**：ProtegoFed（质心的往返）、CrowdGuard（把模型发给客户端评估）。

**风险**：张量一旦能过通道，通道就不再是"小记录"，记录体积和通信量都会上去，需要按插件计量并写进记录。CrowdGuard 要把所有客户端的模型发给每个客户端，通信量是客户端数的平方，论文自己是配合可信执行环境做的，这部分库不提供。

**判断**：可行；Flower 下的握手轮需要先验证。

### 2.4 训练步上的 LoRA 与梯度

**做什么**：训练步视图按需给出当前的 LoRA；接入 `on_pre_optimizer_step`，让插件读取并修改梯度。

**探查结果**：在小模型上跑了 3 步训练。回调在每步都能读到梯度；在回调里把梯度清零后，3 步结束时 LoRA 与开始时逐位相同，说明修改确实作用在参数更新之前。每步之后的 LoRA 也能取到。

**解开**：Safe-FedLLM 步级；TriShield 的主体（梯度投影）。

**做不到的**：
- 回调看到的是整批的梯度，不是逐样本的。差分隐私 LoRA 要逐样本裁剪，仍然做不了。
- 改损失函数（Lisa 的近端项、Obliviate 的正则）仍要继承训练器。

**风险**：设计稿里"训练步不提供干预"这条要改写。每步都跑插件会直接拖慢训练，必须是显式开启。

**判断**：可行，工作量小到中等。

### 2.5 下发前的位置

**做什么**：增加一个服务器侧位置，在全局模型发给各客户端之前运行，允许按客户端改写要发出的对象；第一轮之前也运行一次。

**依据**：Flower 的 FedAvg 是先组一份记录、再按节点复制成多条消息，适配器可以在内层策略返回消息之后逐条改写。**这一点是读源码得出的，没有运行验证。** 单进程适配器里是直接的。

**解开**：EmbTracker。Vaccine、Booster、RepNoise、TAR 也因此有了挂载位置，但它们本身是一整套训练过程，计算要由插件自带，库只提供位置和记录。

**风险**：按客户端下发不同模型后，"服务器的底座等于客户端收到的"这条对照要改成按客户端比。EmbTracker 改的是词嵌入层而不是 LoRA，现在的记录只管 LoRA 的键，要放宽到任意被传输的参数。

**判断**：接口上可行，需要验证；对记录格式有连带改动。

### 2.6 一个插件挂多个位置

**做什么**：允许插件声明多个位置，在各位置之间用自己的状态传递张量。

**解开**：FLTrust、FLAME 各写成一个类；坐标中位数仍需先聚合再替换。

**判断**：纯库内改动，工作量小，没有外部依赖。

### 2.7 仍然进不来的

| 原因 | 论文 |
|---|---|
| 要改损失函数或加训练分支 | Lisa、Obliviate、弱到强蒸馏遗忘 |
| 逐样本梯度的裁剪与加噪 | 差分隐私 LoRA |
| 推理时起作用 | STRIP、PSIM |
| 密码学证明、改聚合协议 | Verifiable Fine-Tuning、FedGT |

共 8 篇。前两行可以通过提供一个可继承的训练器基类来覆盖，但那是另一种扩展方式，不属于"固定位置上挂插件"，我建议先不做。

## 3. 做完之后的覆盖

| | 现在 | 六项做完后（估计） |
|---|---|---|
| 能写（含别扭的） | 21 | 39 |
| 写不了 | 26 | 8 |

39 这个数的构成：现有 21 篇，加上缺接口的 14 篇，加上分发前加固的 4 篇（只是有了位置）。它是按机制推出来的上限，不是验证过的数。真实的数字要靠移植来确认，见第 5 节。

联邦大模型的 6 篇里，做完后 ProtegoFed、Chorus、EmbTracker、Safe-FedLLM、TriShield 都有落点，差分隐私 LoRA 仍然不行。Chorus 是去中心化场景，还需要节点之间的通道，只能算部分。

## 4. 创新性

### 4.1 和现有平台逐项比

| 能力 | 已有的 | fedguard |
|---|---|---|
| 服务器侧分阶段挂防御 | FedSecurity：聚合前、聚合中、聚合后三个函数 | 有，另加收到更新与下发前 |
| 客户端侧挂防御 | FedSecurity 的客户端入口只有数据投毒攻击，防御都在服务器；Flower 的 Mod 和 FLARE 的过滤器只在消息边界 | 训练前、训练步、上传前三个位置 |
| 插件声明自己读什么数据 | 未见。FedSecurity 的防御拿到的是全部本地模型和一个不限内容的附加信息 | 有，启动时核对 |
| 部署条件核对（如安全聚合下拿不到逐客户端更新） | 未见 | 有 |
| 把 LoRA 的 A、B 和乘积作为对象 | 未见，通用平台把更新展平成向量 | 有 |
| 逐轮记录与重放 | **FedDebug（ICSE 2023）已有**，用于调试和定位出错的客户端；BackdoorBench 有按次的文件交接 | 有 |
| 两侧各自记录并按内容哈希对照 | 未见 | 有 |
| 检测与干预分开，未执行的干预也记录 | FedSecurity 有 `get_benign_client_idxs` 一类的接口，其余平台防御的输出就是新的全局参数 | 有 |
| 两侧配对插件及其通道 | Flower 的差分隐私裁剪是"策略包装器加客户端 Mod"的成对实现，但没有抽象成通用通道 | 有 |
| 联邦大模型上的安全实验 | FedSecurity 有 BERT 和 Pythia-1B 的实验，页面上没有提到 LoRA；OpenFedLLM、FedLLM-Bench 没有安全挂点 | 面向 LoRA |
| 集中式微调的安全工具 | SafeTuneBed、SafeTune（2026 年 8 月）统一了多种修复方法 | 不在范围内 |

### 4.2 能站住的创新点

1. **一套契约覆盖两侧。** 文献里至少有 ProtegoFed、Safe-FedLLM、CrowdGuard、Chorus 四个防御必须两侧配合，现有平台都只能在服务器侧挂防御。这是最实在的一点。
2. **面向 LoRA 的对象与检查。** GAP 攻击利用的正是"分别检查 A、B 而不看乘积"。把因子与乘积都作为一等对象，是通用平台没有的。
3. **两侧记录的相互对照。** 服务器作恶的三篇联邦大模型攻击论文里，客户端都没有独立的记录可查。两侧各记一份并按内容哈希对照，不依赖任何检测算法就能发现"发出的和收到的不一致"。
4. **数据需求的显式声明与部署条件核对。** 这让"某个防御在安全聚合下能不能用"变成启动时就能回答的问题。

### 4.3 不能算创新的

- 记录与重放（FedDebug）。
- 服务器侧分阶段注入防御（FedSecurity）。
- 稳健聚合的各种实现（FLPoison、Flower、FedML 都有二十多种）。
- 任何一个内置插件的算法。

### 4.4 创新性的性质与风险

- 这是工具和系统层面的整合创新。它的说服力不来自设计本身，而来自"用它实际写出了多少篇论文的防御"。目前实际写出来的只有昨天试写的 6 个，其中联邦大模型的一个都没有。
- 近期有两篇针对联邦 LoRA 的新防御不在我们的文献库里：FedGraph（ICLR 2026，把客户端更新建成图再聚类）和 Horus（用 LoRA-A 的特征给客户端打分）。从摘要看两者都属于"更新级检测"，现在的契约应该能写，但我只读了检索摘要，没有读全文。
- 领域变化快。SafeTune 是 2026 年 8 月出的；如果有人把类似的统一库做到联邦场景，第 1 点的优势会缩小。

### 4.5 检索的局限

- 创新性的判断只基于昨天的平台调研和今天的三次检索，不是穷尽的。
- FedSecurity 的细节来自工具对论文网页的提炼，其中"客户端没有防御""没有提到 LoRA"这两条我没有逐字核对原文。
- FedDebug 只读了摘要，它具体记录了什么、重放到什么粒度不清楚。

## 5. 建议的做法

按价值和依赖关系排序，每项用"移植一篇具体的论文"作为验收，而不是用接口是否存在：

| 顺序 | 改动 | 用哪篇论文验收 |
|---|---|---|
| 1 | 模型句柄 | GradSentry 或谱签名（只需句柄，最干净） |
| 2 | 训练步的 LoRA 与梯度 | Safe-FedLLM 步级 |
| 3 | 通道传张量与握手 | ProtegoFed（需要第 1 项） |
| 4 | 一个插件挂多个位置 | FLTrust、FLAME |
| 5 | 样本增补与改写 | BEA |
| 6 | 下发前的位置 | EmbTracker |

前三项做完，联邦大模型的防御里最重要的两篇（ProtegoFed、Safe-FedLLM）就能完整写出来，创新点第 1 条才有实证。

每移植一篇，要记录三件事：是否不改库就写成了；与原论文报告的机制是否一致（先不比数值）；该插件每轮的额外耗时。第三件事决定了文档里"低开销"能说到什么程度。

## 6. 需要你定的

1. **是否接受"低开销"只对采集底座成立。** 逐样本梯度一类的插件本身很贵，库只能如实计量，不能让它变便宜。
2. **验收用哪几篇。** 我建议先做 ProtegoFed 和 Safe-FedLLM 两篇，因为它们是联邦大模型上两侧配合的代表，也是项目最初关注的对象。
3. **分发前加固那四篇（Vaccine 等）要不要算进覆盖面。** 它们只是有了挂载位置，方法本身是一整套训练，写成插件意义有限。不算的话覆盖面是 35 篇而不是 39 篇。
