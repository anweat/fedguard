# fedguard 重构设计：按制品与技术组织，而不是按论文（2026-10-10）

## 0. 结论

现在的库有三层：运行时、算子、方法。前两层基本是对的；问题在第三层，它以论文为单位。
这份设计把第三层拆成四样东西，论文退到引用的位置：

| 新的对象 | 回答什么问题 | 增长速度 |
|---|---|---|
| 制品坐标 | 训练过程中有哪些对象，谁在哪里能读、能改 | 很慢，随运行时变 |
| 技术条目（威胁、防御） | 攻击者做的是哪一类事，防御解决的是哪一类问题 | 慢，几十条量级 |
| 实现 | 某个防御技术的一种具体做法（一个插件类或一段算子流水线） | 快，随论文增长 |
| 场景与证据 | 这个实现在哪种攻击、哪种对照下跑过，结果是什么 | 最快，随实验增长 |

攻击和防御不直接互相挂，而是都挂到制品坐标上；"某防御对某威胁有效"只在有证据时才写成一条关系，并且带证据等级。
覆盖情况由这些数据生成，不手写。

运行时与算子库保留，各补两处（§6）。现有 27 个方法类不丢，改登记为大约 14 个防御技术下的实现（§5）。

## 2. 这些框架在同一个问题上的做法

问题是同一个：攻击和防御的条目不断增加，怎样组织才不至于只能一条条追。

### 2.1 攻击与防御怎么关联

| 做法 | 谁这么做 | 特点 |
|---|---|---|
| 防御直接指向攻击技术 | ATT&CK（`mitigates`、`detects`）、ATLAS（`mitigates`，关系上带一段理由） | 简单；关系是人写的，只有"有或没有" |
| 都挂到中间的制品上，再推断关系 | D3FEND：攻击技术与防御技术各自与数字制品关联，攻防关系由此推出 | 新攻击出现时不必有人去逐条连防御；推断出的只是"可能相关" |
| 通过攻击者能力与生命周期位置 | NIST AI 100-2：攻击类由目标、所需能力、阶段、知识定义；缓解措施按部署生命周期的位置组织 | 攻击不是一个名字，而是几个正交维度上的一个点 |
| 检测条目自己引用技术编号，并给覆盖等级 | CAR：每条分析在 `coverage` 里逐个技术写 Low、Moderate；数据侧用（对象、动作、字段）坐标 | 一条检测可以覆盖多个技术，各自的程度不同 |
| 只用标签弱关联 | Sigma（`attack.t1234`）、Atomic Red Team（测试挂在技术编号下） | 内容库不自己维护分类，引用外部编号 |

### 2.2 一个条目写多细

ATT&CK 把抽象层次定在"行为"：战术是目的，技术是做法，具体实现只作为技术下的过程示例，不单独建条目。
D3FEND 的条目是"要解决的技术问题"，同一问题的不同实现归在同一个技术下。
NIST 的攻击类不收具体算法，FGSM、PGD 只在正文里作例子。
三者一致的地方是：**论文和具体算法都不是条目的身份，只是条目下的例子或来源。**

### 2.3 稳定的和增长的分开

OCSF 把骨架（分类结构、字典、基础事件）和条目（事件类、属性、扩展）分成两套变更节奏。
ATLAS 把内容版本和格式版本分开编号。ATT&CK 废弃条目时不删除，留一个指向替代者的指针。
Atomic Red Team 的数据模型禁止未声明的字段，索引和文档由程序生成、不手改。

### 2.4 内容与执行分开，以及这样做的上限

Sigma、CAR、Atomic Red Team、OCSF 都把内容存成数据文件，由独立的工具校验和执行。
Sigma 的规则能写成数据，是因为它表达的是对日志字段的匹配；它自己也分了两级：后端必须支持的特性不支持就报错，可降级的只告警。
CAR 的条目里，检测逻辑是假设与原理的文字加伪代码，具体实现放在 `implementations` 数组里，可以有多种。

### 2.5 覆盖与成熟度

没有一个框架给出单一的覆盖率。ATT&CK 明确说覆盖全部技术不现实，"算不算覆盖"要使用者自己定义。
成熟度的表达各不相同：Sigma 的 `status`（experimental、test、stable、deprecated、unsupported）；ATLAS 技术上的 `maturity`（Feasible、Demonstrated、Realized，资料没有给判定标准）；
CAR 要求每条分析配一个能触发它的单元测试；D3FEND 用来源文档的数量；NIST 没有字段，靠正文叙述，包括"哪些防御后来被攻破"。

## 3. 设计

### 3.1 取谁的做法

- **攻防关联取 D3FEND 加 CAR。** 攻击和防御都登记自己碰哪些制品坐标，由此得到"可能相关"；真正的"有效"关系必须带证据等级（CAR 的分级覆盖），不靠推断。只靠直接连线（ATT&CK、ATLAS）在我们这里行不通：一个防御是否有效取决于它读得到什么、信任谁，二值关系会把这些前提丢掉。
- **攻击的定义取 NIST。** 一个威胁技术是"目标 × 所需能力 × 改动的制品"上的一个点，不是一篇论文的名字。
- **条目的粒度取 ATT&CK 与 D3FEND。** 防御技术是"解决的技术问题"，论文是它下面的实现与来源。
- **内容形式取 Atomic Red Team 与 Sigma。** 条目是带严格模式的数据文件；实现有状态字段，包括"收录但当前跑不了"。
- **验证取 Atomic Red Team 与 CAR。** 每个威胁技术配最小场景，每个实现至少在一个攻击场景和一个无攻击对照下跑过。

不取的：用本体语言描述算法语义（D3FEND）；用来源文档数量当成熟度（D3FEND）；把检测逻辑整个写成数据（Sigma），我们的防御是数值算法。

### 3.2 制品坐标

制品是训练过程中客观存在的对象。它们已经在运行时里，只是现在被当作访问权限，没有当作组织轴。

| 制品 | 在哪一侧 | 可读的位置 | 可改的方式 |
|---|---|---|---|
| 本地样本 | 客户端 | 宣告、训练前 | 屏蔽、改写、增补 |
| 收到的全局 LoRA | 客户端 | 训练前 | 替换 |
| 步内梯度 | 客户端 | 优化器更新前 | 改写 |
| 步内 LoRA 与训练标量 | 客户端 | 每个训练步后 | — |
| 本地更新 | 客户端 | 上传前 | 替换 |
| 上传 | 服务器 | 收到更新、聚合 | 替换、排除、改权重 |
| 聚合结果 | 服务器 | 聚合后 | 替换 |
| 下发内容 | 服务器 | 下发前 | 按接收方改写 |
| 通道消息与张量、自报值 | 两侧 | 握手、训练前、收到更新 | 发送 |
| 模型行为 | 两侧 | 有模型句柄的任何位置 | — |
| 历史 | 两侧 | 任何位置 | — |

坐标仿照 CAR 的数据模型写成三段：`制品 / 取法 / 粒度`，例如 `上传 / 因子差 / 每客户端`、`本地样本 / 逐样本梯度 / 每样本`、`模型行为 / 隐藏状态 / 每样本`。
"取法"基本对应视图和模型句柄已有的方法。条目只引用坐标，不引用具体函数。

另有一张**能力表**（NIST 的做法），描述攻击者控制了什么：控制本地数据、控制本地训练过程、控制上传内容、控制聚合、控制下发内容、多个客户端合谋、能读到防御的参数。每项能力对应它能改动的制品。

### 3.3 四种条目

全部是数据文件（YAML），放在 `fedguard/kb/`，有模式校验，不允许未声明的字段。

**威胁技术 `T-xxxx`**

| 字段 | 含义 |
|---|---|
| `goal` | 后门、破坏安全对齐、降低可用性、隐私等 |
| `capabilities` | 需要能力表里的哪几项 |
| `modifies` | 改动哪些制品 |
| `traces` | 预期在哪些坐标上留下痕迹；每条标明是论文报告的还是推测的 |
| `variants` | 子条目，例如同一做法的不同触发器形式 |
| `sources` | 论文卡片的键 |
| `external` | 对应的 ATLAS、NIST 编号（引用，不复制内容） |
| `evidence` | 只在论文里报告过；我们复现过；见 §3.4 |

**防御技术 `D-xxxx`**

| 字段 | 含义 |
|---|---|
| `tactic` | 观测、检测、隔离（排除或降权）、约束（裁剪、加噪、近端）、净化（改样本、改更新）、修复（聚合后）、证明 |
| `problem` | 解决的技术问题，一句话 |
| `reads` | 读哪些坐标 |
| `acts` | 对哪个制品做什么动作；没有就是只报告 |
| `trust` | 假设谁是诚实的（客户端自己、服务器、多数客户端） |
| `resources` | 需要的外部资源（干净数据、探针、对齐权重对） |
| `always_acts` | 没有攻击时是否也一定会排除或屏蔽些什么 |
| `circumvention` | 已知怎样绕过（D3FEND 登记模板里的一问） |

**实现 `I-xxxx`**

| 字段 | 含义 |
|---|---|
| `technique` | 属于哪个防御技术，只能一个 |
| `entry` | 一个插件类，或一段声明式的算子流水线（§3.5） |
| `params` | 每个参数的论文取值与出处 |
| `deviations`、`open_choices` | 与原文不同之处、原文没说清而我们做的选择；现在写在类说明里，移到这里 |
| `cost` | 以"每样本一次前向""每轮一次 n×n 距离"这样的单位表达 |
| `status` | `experimental`、`tested`、`stable`、`deprecated`、`unsupported`（收录了但运行时还表达不了，写明缺什么） |
| `sources` | 论文卡片的键 |

**场景 `S-xxxx`**

一个可执行的最小实验：模型、客户端构成、哪些客户端有哪项能力、实施哪个威胁技术（或"无攻击"）、规模、种子，以及启动它的参数。相当于 Atomic Red Team 的原子测试。无攻击对照是必备的一种。

### 3.4 关系与证据

- `T modifies 制品`、`D reads 坐标`、`D acts 制品`：登记时写。
- **候选关系**由程序推出：防御读的坐标与威胁留痕的坐标有交集，或防御的动作落在威胁改动的制品上。它只表示"值得试"。
- **`counters` 关系**是一等对象，必须带证据等级和理由：

| 等级 | 含义 |
|---|---|
| 0 | 只是候选，没有任何依据 |
| 1 | 原论文声称有效（记录论文的设定与数值，不作保证） |
| 2 | 在我们的运行时里端到端跑通（没有报错，动作被执行） |
| 3 | 在某个场景下有效果，且无攻击对照里的误伤可接受（附运行记录的哈希） |
| 4 | 在自适应攻击者（知道防御参数）的场景下仍有效果 |

另有一个反向记录：`broken_by`，登记已知在什么条件下失效。NIST 的正文里专门记了"哪些防御后来被攻破"，这一项对我们同样重要。

上两轮实验的结论放进这张表是这样的：26 个实现大多在等级 2；没有一个到等级 3，因为还没有无攻击对照；
LoMar 按原文阈值、CRFL 按原文范数阈值应记 `broken_by: LoRA 因子空间下的默认参数`。

### 3.5 声明式流水线的范围

算子提取里很多防御是"取向量、变换、求距离、聚类、取多数簇、排除"这样的直线流水线，这类可以写成数据：

```yaml
entry:
  pipeline:
    at: server_receive
    read: 上传 / 因子差 / 每客户端
    steps:
      - op: transform.dct_2d
      - op: transform.low_frequency_triangle
      - op: cluster.distances
        args: {metric: cosine}
      - op: cluster.majority_cluster
    decide: exclude_outside
```

跨位置带状态的、要握手的、要在循环里调模型的，仍然写成类，`entry` 指向类名。
这不是为了省代码，而是为了让"一篇新论文"在多数情况下只是一段新的组合；组合不出来时，缺的那个算子或坐标就是要补的东西。
先做直线流水线一种形式，不做条件、循环。

### 3.6 新东西来了怎么判

仿照 ATT&CK 的三条路径：

| 情况 | 处理 |
|---|---|
| 读的坐标、动作、信任假设都与某个已有防御技术相同，只是算子或参数不同 | 该技术下的一个新实现 |
| 同一技术问题，但读了新的坐标或需要新的资源 | 该技术的子条目 |
| 解决的技术问题不同，或信任假设不同 | 新的防御技术 |
| 需要运行时没有的制品、位置或动作 | 先登记为 `unsupported`，并在运行时的缺口清单里记一条 |
| 不碰任何制品（例如纯协议、纯密码学证明） | 不收录为技术，只在边界声明里列出 |

威胁侧同理：能力和改动的制品都相同的，是变体；需要新能力或改动新制品的，才是新技术。

### 3.7 覆盖怎么表达

不给百分比，生成三张表（生成物不手改）：

1. **制品 × 战术**：每格列出防御技术及其最高证据等级。空格就是没有手段的地方。
2. **威胁技术 × 防御技术**：格子里是证据等级；候选但没试过的显示为 0。
3. **缺口清单**：所有 `unsupported` 的实现，按缺的运行时能力归并。

## 4. 现状放进这个结构是什么样

按 27 个方法类的声明统计（由程序读出）：

| 制品 | 读它的方法数 | 对它有动作的方法数 |
|---|---|---|
| 上传 | 13 | 3（替换）＋11（排除或改权重） |
| 聚合结果 | 6 | 5 |
| 本地样本 | 5 | 6 |
| 模型行为 | 6 | — |
| 通道与自报值 | 5 | — |
| 收到的全局 LoRA | 2 | 1 |
| 步内梯度 | 2 | 2 |
| 步内 LoRA 与训练标量 | 1 | — |
| 本地更新 | 1 | 1 |
| 下发内容 | 0 | 0 |
| 历史 | 0 | — |

这张表说明了三件按论文组织时看不出来的事：

- 方法高度集中在"上传"上，而且几乎都是"排除或改权重"。
- "下发内容"上没有任何方法，尽管 137 篇里有 26 篇的攻击入口是模型分发。
- "历史"这个数据类别没有方法声明使用；FoolsGold、FLDetector、MUD-HoG、MCD 都自己在插件状态里攒历史，说明这个视图的设计不合用。

另一个信号：算子提取的 511 个步骤里用了 488 个不同的算子名。名字没有受控，同一个计算在不同论文的提取里叫法不同，所以现在无法回答"哪些算子被多少方法复用"。

## 5. 现有 27 个类归并成的防御技术（初稿）

| 防御技术（解决的问题） | 战术 | 现有实现 |
|---|---|---|
| 同轮更新的几何离群筛选 | 检测、隔离 | Krum、LoMar、FLAME 的聚类部分、FreqFed |
| 逐坐标的稳健聚合 | 约束 | 坐标中位数、截尾均值 |
| 跨轮行为一致性 | 检测、隔离 | FoolsGold、FLDetector、MUD-HoG、MCD |
| 以可信参照更新定信任 | 隔离 | FLTrust |
| 更新范数约束与加噪 | 约束 | 范数裁剪、FLAME 的裁剪与加噪、CRFL |
| 适配器权重上的探针分类 | 检测、隔离 | Safe-FedLLM 客户端级、步级 |
| 样本表示离群 | 检测、净化 | 谱签名、激活聚类 |
| 逐样本梯度离群 | 检测、净化 | 梯度谱熵、ProtegoFed（带跨客户端参照的子条目） |
| 文本表层净化 | 净化 | ONION |
| 安全样本增补 | 约束 | 安全样本混入、BEA（带秘密前缀的子条目） |
| 本地优化步约束 | 约束 | Lisa 近端项、LA-LoRA 本地步 |
| 收到模型的结构检查 | 检测、净化 | TriShield 适配器扫描 |
| 上传前的更新投影 | 净化 | TriShield 更新投影 |
| 聚合后的子空间修复 | 修复 | Safe LoRA |

27 个类落在 14 个技术里。这是我的初步归并，边界有可以争的地方（例如 FLAME 被拆进两个技术）。

## 6. 运行时与算子库要改的

| 改动 | 原因 |
|---|---|
| 坐标表成为受控词表，视图与句柄的方法与它一一对应 | 条目引用坐标而不是函数；现在的数据类别只到制品一级 |
| 历史视图重做 | 四个跨轮方法都绕开了它 |
| 插件声明里把必需与可降级分开 | 现在缺任何一项就拒绝启动；Sigma 的两级更合用（例如没有模型句柄时降级为只看权重） |
| 算子名受控，每个算子声明输入类型与适用假设 | 488 个名字无法统计复用；NIST 卡片的建议是让算子声明失效边界 |
| 记录里写入知识库的内容版本与格式版本 | 要能回答"那次运行用的是哪一版防御组合"（ATLAS 的两套版本号） |
| 可替换损失与逐样本梯度的训练器子类 | 上一轮发现的两个缺口；它们会成为缺口清单里最先出现的两条 |

不改的：11 个位置、动作集合、两侧记录与对照、通道。

## 7. 没有解决的问题

- **推断出的候选关系会很多。** 几乎所有读"上传"的防御都与所有改"上传"的威胁相交。要靠粒度和取法把坐标分细，否则候选表没有信息量。坐标分到多细合适，要在迁移现有条目时试出来。
- **威胁侧的留痕字段大多只能填"推测"。** 攻击论文很少报告自己在哪里可观测。这一栏的价值取决于我们自己的场景实验。
- **证据等级 3 的"误伤可接受"需要一个数。** 我还没有提议阈值，它可能要按战术分别定。
- **防御技术的归并是主观的。** 两个人可能分出不同的 14 类。ATT&CK 靠编辑团队裁决，我们需要一份成文的判据（§3.6 是初稿），并接受它会改。
- **知识库本身要维护。** 条目多了以后登记与核对是持续的工作。DeepSeek 可以按模式产出初稿，但 `counters` 关系和证据等级必须来自运行记录，不能来自模型的判断。

## 8. 建议的步骤

| 步 | 内容 | 产出 | 需要算力 |
|---|---|---|---|
| 1 | 定坐标表、能力表、四种条目的模式，写校验器 | `fedguard/kb/` 的骨架 | 否 |
| 2 | 把 27 个类登记为实现，归到防御技术下；把类说明里的偏离与选择移进条目 | 约 14 个 `D`、27 个 `I` | 否 |
| 3 | 让 DeepSeek 按模式把 60 篇攻击论文卡片归成威胁技术初稿，我核对合并 | 约 20 到 30 个 `T` | 否 |
| 4 | 生成三张表，看空格和候选 | 第一版覆盖视图 | 否 |
| 5 | 建场景：无攻击对照、有害数据客户端、后门样本各一个，把现有批量脚本改成按场景跑 | `S` 条目与证据等级 2、3 的第一批数据 | 是 |
| 6 | 受控算子词表；把直线流水线类的实现改写成声明式 | 算子复用统计 | 否 |
| 7 | 按缺口清单补运行时 | 训练器子类等 | 部分 |

第 1 到 4 步不改现有代码的行为，只是加一层数据并重新登记。我建议先做这四步，看到表以后再决定第 5 步之后的顺序。
